## 2. 执行方式

Jasna 和 Vela 是两个独立项目，分别使用各自已有的启动命令。Mengsk 执行并审阅结果。每个项目每个运行批次只保留一份日志，stdout 与 stderr 合并写入。Vela 继续使用现有单视频或批量启动命令，自动创建日志并同步输出到控制台，无需额外日志脚本；`info`、帮助与版本查询不创建视频任务日志。

一个批次可以处理一个或多个视频。多个视频串行时，在同一文件中依次追加每个视频的“任务开始 → 处理目标 → 处理日志 → 处理完毕”；失败、中断或跳过时使用对应结果名称。上一个视频结束后才开始下一个，每行都带项目名、输入文件名和任务序号。视频内部的多 GPU 分段处理不改变视频之间的串行关系。

## 3. 输出位置

日志放在启动命令所在工作目录的 `.tmp/restoration-order/private/runtime-logs/<run-id>/`，`<run-id>` 标识一次运行批次。Vela 自动生成包含时间和随机标识的运行编号，独占创建文件以避免覆盖；批次开始行显示日志路径：

- `jasna.log`：该批次全部 Jasna 视频任务的完整日志。
- `vela.log`：该批次全部 Vela 视频任务的完整日志。

例如 Vela 连续处理 20 个视频，全部写入同一个 `vela.log`，不按视频拆成 20 份。只运行其中一个项目，就只生成对应的一份日志。重跑使用新的运行编号，不覆盖上次记录；不另建状态 JSON、查看版或索引文件。

日志从新批次开始时记录，历史采集只留档，不纳入本次对照。日志目录受 Git 忽略；公开文档不复制真实片名、连接信息或私有部署路径。

## 4. 输出内容

### 4.1 任务开始

一行说明“谁、处理哪个视频、输入是什么、何时开始”：

```text
时间 项目 输入文件 [序号/总数] 任务开始 输入=480p(854x480)@60fps 视频码率=5.000Mbps 视频时长=60秒
```

行首时间就是开始时间，包含日期；时区在批次开始注明。分辨率同时保留宽高，帧率使用实际探测值，例如 `59.94fps` 不写成 `60fps`。不同目录存在同名文件时，显示相对输入根目录的路径，并以序号区分。

### 4.2 处理目标

下一行列出本次视频的生效目标：分辨率、帧率、编码器、目标码率、码率上限、质量参数和模型。配置目标与实际传给编码器的值不同时，在该行说明差异；未显式设置写“未设置”，未取得参数写“未记录”。

输入与输出摘要的“视频码率”均指视频流平均码率；“目标视频码率”指编码配置，“码率上限”指 `maxrate`。CQ／CRF 是单独的无单位质量参数，不能替代码率。码率统一用十进制 Mbps，`1 Mbps = 1,000,000 bit/s`。

码率来源在同一日志的参数记录中注明。只有文件总码率时，视频码率写“无法获取”，另列文件总码率，不能混用。Jasna 和 Vela 都可能回退到容器码率，Jasna 还会尝试视频流标签；Vela 内部值也可能为 0 或回退值 2500 kbps。回退值不能记作测量结果。Vela 的低码率保护或软件编码回退可能不传配置目标；Jasna 上限可能按输入值自动推导，因此须记录实际编码参数。

Vela 在批次开头记录一次解析后的生效配置，不抄录环境凭据。任务开始行注明输入码率来源，结束前记录输出元数据来源；每个视频仍保留自己的开始和目标行。有差异时随该任务明确记录，不需要逐字段拆成多行。

Vela 的目标行先记录配置码率和实际分辨率／帧率；各 worker 确定编码器后，再在该任务的“处理日志”中记录“生效编码参数”，列出真实编码器、码控模式、CQ／CRF、目标与上限。相同 worker 参数不变时不重复打印，参数变化时重新记录。

### 4.3 处理日志

程序原生输出前加上该视频的时间、项目名、文件名、任务序号和“处理日志”，保留原始正文。阶段进度、告警、错误及异常堆栈均写入同一个文件；多行堆栈每行带相同任务标识，避免归到下一个视频。

程序提供哪些进度就记录哪些，普通进度沿用原生输出频率。阶段变化、封装及完成消息完整保留。程序提供过程码率时，保留其实时值或累计平均值含义；它不替代最终输出码率。处理速度 fps 与视频帧率分别命名。不新增 benchmark、定时采样或独立错误日志。

多卡性能信息也写在同一份日志：

- 调度时区分发现的 GPU 与实际启动的 worker，列出实际数量和设备编号；分段少于卡数时明确只启动相应数量。
- 每卡记录初始化开始、完成耗时、实际推理后端及模型是否加载；通用库输出和异常堆栈带设备标识。
- 每段记录开始、进度、完成耗时与速度；首批处理单独记录开始和结束，耗时包含数据转换、推理、传输及可能的首次编译，不冒充纯计算耗时。
- 在初始化和分段完成时记录资源快照：进程的 PyTorch 已分配／保留／峰值显存，与整卡显存、利用率、温度、功耗分别命名。整卡指标可能包括其他进程，瞬时值不作为平均利用率；查询不可用时说明原因，不影响处理。
- 全局进度保留完成分段数、处理帧数、累计平均速度及 ETA，并用 `Resumed` 单列复用段。ETA 只依据本轮实际处理段估算，复用段不进入速度样本；尚无新处理段完成时显示 `pending`。首轮并行分段尚未完成时不作为稳定耗时预测。

Linux 在捕获原生输出前启动多进程资源跟踪进程，避免其持有任务日志管道而影响收尾。日志持久化目录须位于容器外的挂载目录，以便容器退出后继续查阅。

### 4.4 处理结果

每个视频用一行集中呈现结果，成功行使用“处理完毕”：输出位置、实际分辨率、视频帧率、最终视频平均码率、文件大小、处理时长、处理速度及处理帧数。文件总平均码率作为独立字段，便于核对大小。

- **处理时长**：该视频从任务开始到完成的墙钟耗时，包含该任务的初始化和封装；视频时长是另一个字段。
- **处理速度**：该视频已处理帧数 ÷ 处理时长（秒）。它是整个任务的平均速度，与视频帧率、过程中的瞬时速度分别记录。帧数不可得时写“未记录”。复用已完成分段时，记录复用原因；“处理帧数”只计本轮新处理的帧，全部复用时为 0，速度为 0fps，不冒充输出总帧数。
- **码率与大小**：封装完成后从最终文件取得，记录来源。大小统一用十进制 MB／GB，不用含义不明的 G。按 `文件字节数 × 8 ÷ 视频时长（秒）` 计算的值标为“文件总码率（按大小估算）”，不能当作视频流码率。
- **失败、中断**：使用“处理失败”或“任务中断”，记录错误原因、处理时长和输出是否完整；输出未确认完成时不填写成功产物指标。无法取得的码率写“无法获取”，未采集字段写“未记录”。

单个视频成功依据对应任务正常返回、封装及完成记录确认。在一个进程内串行处理多个视频时，视频任务没有各自的进程退出码；真实退出码只写在批次结束行。若由多个原生命令串行运行，只有实际取得该命令退出码时才记录为“命令退出码”，不能推测。

### 4.5 串行批次与异常

批次开头一行记录运行编号、任务总数、时区和原生失败策略；结尾一行记录成功、失败、跳过、未处理数量、批次总耗时及实际进程退出码。正常结束时应满足 `总数 = 成功 + 失败 + 跳过 + 未处理`。总数以本批次候选队列为准，不把扫描时已排除的文件算入跳过。

Vela 原生批量入口按排序后的候选列表串行处理，单个视频异常后继续下一个。已有输出或输入高度达到目标时会跳过，以“任务跳过 原因=…”单行记录，不算本次成功处理，也不必为未启动的任务伪造开始、目标和进度。

Vela 当前批量入口在遍历完成后返回 0，即使其中有失败；因此批次有失败时，摘要须写“存在失败”，不能因退出码 0 写成全部成功。跳过已有输出也不代表校验过该文件。Jasna 的停止或继续行为以所用原生入口的实际行为为准，不能套用 Vela 的策略。

批次中断时，已经结束的视频保留原结果，当前视频记为中断，剩余队列记为未处理，并单列中断数量；此时汇总校验增加中断项。无法取得结果尾行时只能判为“缺少结束记录，结果未知”，不补造成功或退出码。批次总耗时独立计时，可能包含任务间开销。

## 5. 预期输出样例

### 5.1 阅读约定

以下文件名、时间、进度、码率和大小均为示意数据，不是运行或性能测试结果。新格式为：

```text
YYYY-MM-DD HH:mm:ss 项目 输入文件 [序号/总数] 事件 正文
```

批次行不属于某个视频，文件位置使用 `-`，任务位置使用 `[批次]`。Vela 已实现时间戳、任务标识、集中摘要和最终元数据记录。样例为便于阅读省略部分配置、元数据来源和重复进度行；Jasna 尚未实施此格式。原生进度条在示例中作换行简化展示，部分重复行省略；实际保留原始正文。

### 5.4 单个失败后继续，已有输出则跳过
